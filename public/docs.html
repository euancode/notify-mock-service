GOV.UK Notify MOCK
Dashboard API docs

API documentation

This service mimics the subset of the GOV.UK Notify REST API needed to send and track SMS and email notifications, so you can develop and test against it without a real Notify account. Responses are shaped the same as the real API, but delivery is simulated locally — nothing is actually sent.

Base URL: https://your-deployment.example.com — replace with wherever you've deployed this service (or http://localhost:3000 when running locally).

Authentication

The real Notify API requires a Authorization: Bearer <jwt> header, where the JWT is signed with your API key's secret. This mock does not cryptographically verify that signature — it only requires that an Authorization header is present. This means the official Notify client libraries (Node, Python, .NET, etc.) work against this server unchanged: just point their base URL here and use any API key value.

HeaderRequiredNotes
Authorization Yes Any value accepted, e.g. Bearer test_key-00000000-0000-0000-0000-000000000000-00000000-0000-0000-0000-000000000000. Missing header returns 401.

Send an SMS

POST/v2/notifications/sms
FieldTypeRequiredDescription
phone_numberstringYesRecipient phone number, e.g. +447700900000.
template_idstring (uuid)YesOne of the seeded template IDs below, or any UUID (an ad-hoc template is created on the fly).
personalisationobjectIf the template needs itKey/value pairs substituted into ((placeholders)) in the template body.
referencestringNoYour own identifier, echoed back and filterable via GET /v2/notifications.
curl -X POST https://your-deployment.example.com/v2/notifications/sms \
  -H "Authorization: Bearer test_key" \
  -H "Content-Type: application/json" \
  -d '{
    "phone_number": "+447700900000",
    "template_id": "8a5e1b3a-0000-4000-8000-000000000001",
    "personalisation": { "code": "482913" },
    "reference": "signup-482913"
  }'
{
  "id": "b6c1...",
  "reference": "signup-482913",
  "content": {
    "body": "Your verification code is 482913. It expires in 5 minutes.",
    "from_number": "GOVUK"
  },
  "uri": "https://your-deployment.example.com/v2/notifications/b6c1...",
  "template": {
    "id": "8a5e1b3a-0000-4000-8000-000000000001",
    "version": 1,
    "uri": "https://your-deployment.example.com/v2/template/8a5e1b3a-0000-4000-8000-000000000001"
  }
}

Watch the dashboard after sending — the message appears on the mock phone within a second.

Get a single notification

GET/v2/notifications/{id}

Returns the current status of a previously created notification.

{

List notifications

GET/v2/notifications

Supports optional query filters: status, template_type (sms/email), reference.

GET /v2/notifications?status=delivered&template_type=sms

Using any other UUID as template_id creates an ad-hoc template on the fly, expecting a message personalisation field (and subject for email).

Notification lifecycle

Every created notification moves through statuses automatically, roughly matching real-world timing and outcome distribution:

StatusWhen
createdImmediately on creation.
sending~0.6–1.5s later.
deliveredMost common final state (~88% of notifications), a few seconds after sending.
permanent-failure / temporary-failure / technical-failureRandomly assigned to the remaining ~12%, to help you test failure handling.
Mock-only feature: to force a specific outcome instead of the random one, add _mock_status to your personalisation object, e.g. "personalisation": { "_mock_status": "permanent-failure" }. This key is stripped before template rendering and isn't part of the real Notify API.

Errors

Error responses match the real API's shape:

{
  "errors": [
    { "error": "ValidationError", "message": "phone_number is a required property" }
  ],
  "status_code": 400
}
StatusCause
400Missing/invalid phone_number, email_address, template_id, or missing personalisation values required by the template.
401Missing Authorization header.
404Notification or template ID not found.

What isn't mocked

  • No real SMS/email is ever sent — everything is simulated in memory.
  • Notification and template data is not persisted; it resets whenever the server restarts.
  • Letters, precompiled PDF letters, and the "received text messages" inbound SMS API aren't implemented.
  • API key signatures aren't cryptographically verified.
